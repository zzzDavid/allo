# Symbolic performance reasoning for Allo

The shape of an Allo accelerator's cycle count is fixed by what's already in the post-schedule MLIR — loop nest, pragma placement, partitioning, body ops. Only a few values — per-loop II, body iteration latency, dataflow stage rates — need synthesis or measurement to know. If the user declares those as symbols, the compiler can build a cycle expression for the whole accelerator without ever running synthesis in the inner loop.

That expression unlocks four things:

  1. **Prediction** — cycle count fast, before synthesis.
  2. **Attribution** — answer "why is performance like this?".
  3. **Sensitivity / what-if** — "what would change if I improved X?".
  4. **Self-optimization** — drive an auto-scheduler with a symbolic cost model and prove dominance between schedules.

The underlying recursion is just the standard HLS formula: for a loop `L` with trip count `N_L`, II `II_L`, and body latency `lat_L`,

  Cycles(L) = (N_L − 1) · II_L + lat_L

with `lat_L = Cycles(inner)` when `L` is not a leaf, and `II_L = lat_L` when `L` is not pipelined. The compiler walks the post-schedule loop tree bottom-up and builds a SymPy expression in this form.


## Interface design

The whole API is six methods. Four of them produce SymPy expressions that the user manipulates with `sympy.simplify`, `sympy.diff`, `sympy.solve`, `subs`, and friends — there are no specialized `compare` / `sensitivity` / `bottleneck` methods, because those are just one-liners in SymPy once you have the expression. The two non-SymPy methods are for things SymPy can't do: causal IR analysis and counterfactual transformation simulation.

```python
# Declare / bind / build  (produce SymPy expressions)
s.perf_var(target, *fields)                       # → symbol or tuple of symbols
s.concretize(target, *, reason=None, **values)    # bind values to symbols
s.estimate_cycles(*free_vars)                     # → sympy.Expr
s.cycles_by_loop(*free_vars)                      # → dict[loop_path, sympy.Expr]

# IR analysis  (not SymPy operations)
s.explain(target)                                 # provenance + dep-graph derivation
s.suggest_fixes(loop)                             # counterfactual fixes
```

### Targets are loops, functions, or ops

`perf_var` and `concretize` both take a single positional `target` whose kind is detected from its form:

  - **Loop**: `"function_name:loop_path"` (path-style, contains `:`). Fields: `"ii"`, `"lat"`, `"trips"`.
  - **Function**: `"function_name"` (bare name, resolves to a function in the schedule's IR). Fields: `"L"` (full latency), `"II_steady"` (steady-state rate).
  - **Op**: `"op_name/dtype/target"` (e.g. `"arith.addf/f32/vhls"`). Fields: `"lat"`. Op-target operations have global effect — calling them on any schedule binds the same symbol everywhere.

Fields are validated against the target kind. Mismatches raise immediately.

### `perf_var` returns the symbols you declared

```python
ii_k, lat_k = s.perf_var("gemm:k.inner", "ii", "lat")     # tuple
lat_addf    = s.perf_var("arith.addf/f32/vhls", "lat")    # single symbol
L, II_st    = s.perf_var("compute_stage", "L", "II_steady")
```

The returned objects are plain SymPy `Symbol`s. They are *uniqued* on stable keys (see below), so two schedules of the same function get literally the same `Symbol` object back from their respective `perf_var` calls. This is what makes downstream SymPy operations (`expr_a - expr_b`, `simplify`, etc.) cancel cleanly.

### `concretize` binds values, with provenance

```python
s.concretize("gemm:k.inner", ii=4, lat=12,
             reason="dep-graph analysis: RAW on C[i,j] via fadd")

s.concretize("arith.addf/f32/vhls", lat=4,
             reason="vendor datasheet, Vitis HLS 2023.2")

s.concretize("conv2d:c", ii=8, lat=20,
             reason="AXI master read, burst=16, measured cosim 2026-04 on U280")
```

`reason=` is a free-text provenance string. It does not affect the solver (the value is always taken as ground truth) — it exists so `s.explain(...)` can later tell the user *where the number came from*. This matters six months in, when someone reads the schedule and wants to know whether a cost is grounded in measurement or someone's guess.

### `estimate_cycles` takes its free variables explicitly

```python
ii_k, lat_k = s.perf_var("gemm:k.inner", "ii", "lat")
expr = s.estimate_cycles(ii_k, lat_k)
```

The args serve two purposes:

  1. They make the expression's dependencies obvious at the call site — you can see which symbols feed in.
  2. They are a *contract*: after building, the compiler checks that the expression's actual free variables are exactly the ones you passed. If you forgot to declare a perf var for some loop the walker visits, you get an error (see below). If you passed a symbol that doesn't appear in the result, you also get an error — usually a sign you declared something for the wrong loop.

`s.estimate_cycles()` with no args is valid only when every value in the expression is concrete (no free variables remain).

### `cycles_by_loop` for per-loop attribution

```python
contribs = s.cycles_by_loop(ii_k, lat_k)
# {'gemm:i':  ...,
#  'gemm:j':  ...,
#  'gemm:k.inner': M*N*((K-1)*ii_k + lat_k)}
```

This is the only thing not directly available from the SymPy expression alone — once the compiler has summed terms and SymPy has simplified, the "this term came from loop k" attribution is lost. `cycles_by_loop` returns a dict mapping each loop to its symbolic contribution. Used for bottleneck analysis (`max(contribs.items(), key=...)`), Amdahl-style attribution, and per-loop sensitivity.

### Errors instead of fallbacks

When `estimate_cycles` walks the loop tree, for each `(loop, attribute)` it consults sources in this order:

  1. User-declared symbol (`perf_var`)
  2. User-concretized value (`concretize`) or synthesis cache
  3. IR-derived constant (e.g. trip count from `affine.for` bound)
  4. Otherwise → `PerfModelError` listing exactly what's missing

```
PerfModelError: cannot build cycle expression for function 'gemm':

  loop 'gemm:k.outer'  missing: ii, lat
  loop 'gemm:k.inner'  missing: ii, lat

Each missing value must be either declared symbolic or concretized:
  s.perf_var("gemm:k.outer", "ii", "lat")    # keep symbolic
  s.concretize("gemm:k.outer", ii=1, lat=2,
               reason="...")                  # bind to a value

Trip counts for these loops were inferred from the IR:
  gemm:k.outer  trips = K/8     (affine bound)
  gemm:k.inner  trips = 8       (affine bound)
```

Plus the contract check on `estimate_cycles` args:

```
PerfModelError: free variables in estimate_cycles do not match expression:
  passed but unused:    lat_gemm_j     (forgot to declare a loop?)
  used but not passed:  ii_gemm_k_inner
```

The user controls what stays symbolic. Nothing is silently inferred from hidden tables.

### Sharing across schedules: uniquing

Perf vars are uniqued on stable keys, so two schedules that name the same target get the literally-same SymPy `Symbol` back. (Same idea as MLIR's type and attribute uniquing — structurally-equal things resolve to the same object.) Three keys:

  - **Loop**: `(function_name, loop_path)` — two schedules of the same function share that loop's `ii` / `lat` symbols.
  - **Function**: `function_name` — two parents that compose the same sub-function share its `L` and `II_steady` symbols.
  - **Op**: `(op_name, dtype, target)` — global; a body-op latency is a physical constant of the device, so it interns project-wide.

Uniquing is what makes `sympy.simplify(expr_a - expr_b)` honest — the common terms cancel because the symbols *are* the same object, not because of name matching.

### Hierarchical perf modeling for compose / dataflow

A function has two levels of perf abstraction:

  - **As a box**: atomic symbols `L_f` (latency) and `II_f` (steady-state rate), declared with `s.perf_var("f", "L", "II_steady")`. Useful early, when `f` is a black-box IP, or when reasoning about a dataflow region without committing to its internal schedule.
  - **Expanded**: `L_f` and `II_f` are themselves expressions over `f`'s internal loop perf vars, built recursively by walking `f`'s loop tree. This happens automatically when the sub-schedule has its own `perf_var` / `concretize` declarations.

For a dataflow region with stages `S_1 … S_k` processing `T` tokens:

  Cycles_dataflow  =  max_i (L_{S_i})  +  (T − 1) · max_i (II_{S_i})

The unit of abstraction is the function. `s.compose` already gives Allo hierarchical schedules; the perf model rides on the same hierarchy. For stages where steady-state II isn't simply the inner-loop II (burst, FIFO backpressure stalls), fall back to "box" plus a `concretize` from profiling. Hierarchical modeling is a default, not a contract.

### Causal explanation: derived from the IR, not narrated

`s.explain(target)` and `s.suggest_fixes(loop)` are the two non-SymPy methods — they don't operate on the cycle expression, they operate on the IR directly. Three real sources of causal information:

**Recurrence bound on II.** Walk def-use chains in the loop body, find carried dependences, compute `II ≥ ⌈chain_lat / dist⌉`. The cycle itself is the explanation.

**Resource bound on II.** Count loads/stores per array per iteration, compare against the array's partition factor. Emit the binding access pattern.

The actual `II` is `max(II_recurrence, II_resource)`; `s.explain` reports which bound is binding.

**Counterfactual transformation.** Once the binding bound is known, `s.suggest_fixes` mechanically simulates candidate fixes by re-running the analysis on the IR after a hypothetical schedule primitive — `buffer_at` to lift a carried dep, `partition` to add ports, etc. It doesn't actually apply the transformation; it just knows how each primitive perturbs the dep graph and port counts. The output is a ranked list of fixes with predicted II values, including ruled-out fixes ("not a port-bound loop").

Real causal reasoning, no LLM, no canned strings — just dep-graph walks and a small table of what each schedule primitive does to the dep graph and port counts.


## Concrete examples

All examples assume `import sympy` is in scope.

### Example 1 — Comparing two GEMM schedules

```python
def gemm(A: "float32[M,K]", B: "float32[K,N]", C: "float32[M,N]"):
    for i, j in allo.grid(M, N):
        for k in allo.reduction(K):
            C[i, j] += A[i, k] * B[k, j]

# Schedule A: pipeline k directly (carried dep on C[i,j] hurts II)
s_a = allo.customize(gemm)
s_a.split("k", 8); s_a.pipeline("k.inner")
ii_a, lat_a = s_a.perf_var("gemm:k.inner", "ii", "lat")

# Schedule B: same split, but break the carried dep with buffer_at
s_b = allo.customize(gemm)
s_b.split("k", 8); s_b.buffer_at(s_b.C, "i"); s_b.pipeline("k.inner")
ii_b, lat_b = s_b.perf_var("gemm:k.inner", "ii", "lat")

# ii_a is ii_b  →  True   (uniqued on (gemm, k.inner, ii))
# lat_a is lat_b →  True

expr_a = s_a.estimate_cycles(ii_a, lat_a)
expr_b = s_b.estimate_cycles(ii_b, lat_b)

# Compare with raw SymPy:
delta = sympy.simplify(expr_a - expr_b)
# Both expressions share II and lat, so the structural part cancels.

# Concretize from compiler dep-graph analysis:
s_a.concretize("gemm:k.inner", ii=4,
               reason="recurrence: RAW on C[i,j] via fadd, lat=4, dist=1")
s_b.concretize("gemm:k.inner", ii=1,
               reason="dep broken by buffer_at(C, 'i')")

# Now substitute and simplify:
delta_concrete = sympy.simplify(delta.subs({ii_a: 4, ii_b: 1}))
# → M*N*(K-1)*3   cycles in B's favor
```

The user wrote no formula. They declared knobs, let the compiler build, and used SymPy directly to compare.

### Example 2 — Bottleneck attribution via `cycles_by_loop`

```python
def kernel(...):
    load_inputs(...)        # → load_term
    compute(...)            # → compute_term
    store_outputs(...)      # → store_term

s = allo.customize(kernel)
# (declare perf_vars for each phase's inner loops...)

contribs = s.cycles_by_loop(*free_vars)
# {'kernel:load:i':    ... ,                              # = M*K*α_load
#  'kernel:compute:k': M*N*K*α_compute + low-order ... ,
#  'kernel:store:i':   M*N*β_store}
```

Now everything else is SymPy:

```python
# (a) Asymptotic dominance — which term grows fastest in K?
{loop: sympy.degree(expr, K) for loop, expr in contribs.items()}
# {'kernel:load:i': 1, 'kernel:compute:k': 2, 'kernel:store:i': 0}
# → compute dominates as K → ∞ (highest degree in K).

# (b) Conditional crossover — where does compute overtake load?
sympy.solve(contribs['kernel:compute:k'] > contribs['kernel:load:i'], K)
# → K > α_load / α_compute   (the operating regime where compute wins)

# (c) Range analysis — for K in [16, 1024], everything else fixed:
[(loop, expr.subs({K: k_val}))
   for k_val in [16, 256, 1024]
   for loop, expr in contribs.items()]

# (d) Concrete bottleneck — substitute everything, take the max:
concrete = {loop: float(expr.subs(values)) for loop, expr in contribs.items()}
max(concrete.items(), key=lambda kv: kv[1])
# → ('kernel:compute:k', 159383552.0)

# Amdahl-style attribution:
total = sum(concrete.values())
{loop: v/total for loop, v in concrete.items()}
# → {'kernel:compute:k': 0.87, ...}
```

Modes (a) and (b) are where the symbolic form pays for itself — zero synthesis runs, and the answer is structural ("compute scales one degree higher in K"), not just a number.

### Example 3 — Causal explanation, derived from the IR

```python
s = allo.customize(gemm)
s.split("k", 8); s.pipeline("k.inner")
ii_k, lat_k = s.perf_var("gemm:k.inner", "ii", "lat")

s.explain("gemm:k.inner")
# IIBound(
#   loop  = "gemm:k.inner",
#   binding = "recurrence",
#   value = 4,
#   recurrence = IIRecurrence(
#     cycle = [load(C[i,j]) @ lat=2,
#              mulf          @ lat=0,
#              addf          @ lat=4,    # critical
#              store(C[i,j]) @ lat=1],
#     chain_latency = 4,
#     distance      = 1,
#     formula       = "ceil(4 / 1) = 4",
#   ),
#   resource = IIResource(value=1, reason="2 reads on B, 2 BRAM ports"),
# )

s.suggest_fixes("gemm:k.inner")
# 1. buffer_at(C, "i")     predicted II=1   removes carried dep on C
# 2. unroll(k.inner, 4)    predicted II=4   dep still in critical path
# 3. partition(C, "i", 2)  predicted II=4   not a port-bound loop
```

Both are computed by walking the IR. The cycle is found by a standard def-use traversal on the body; the fix ranking is computed by mechanically applying each candidate primitive's effect to the dep graph and re-deriving II. Not a SymPy operation — that's why this is one of the two methods that isn't replaceable by `sympy.something`.

### Example 4 — Sensitivity / what-if

```python
ii_k, lat_k = s.perf_var("gemm:k.inner", "ii", "lat")
expr = s.estimate_cycles(ii_k, lat_k)
# = M*N*((K-1)*ii_k + lat_k)

sympy.diff(expr, ii_k)    # = M*N*(K-1)
sympy.diff(expr, lat_k)   # = M*N
```

A 1-cycle improvement in II is `(K−1)×` more valuable than the same improvement in lat. This drops directly out of `sympy.diff` — no specialized `s.sensitivity` is needed.

### Example 5 — Hierarchical dataflow

```python
s_load    = allo.customize(load_stage)
s_compute = allo.customize(compute_stage)
s_store   = allo.customize(store_stage)

s = allo.customize(top)
s.compose(s_load); s.compose(s_compute); s.compose(s_store)
s.dataflow("top:main_loop")

# Option A — treat each stage as a box (early, before scheduling internals)
L_load,    II_load    = s.perf_var("load_stage",    "L", "II_steady")
L_compute, II_compute = s.perf_var("compute_stage", "L", "II_steady")
L_store,   II_store   = s.perf_var("store_stage",   "L", "II_steady")

expr = s.estimate_cycles(L_load, II_load, L_compute, II_compute, L_store, II_store)
# = sympy.Max(L_load, L_compute, L_store)
#   + (T - 1) * sympy.Max(II_load, II_compute, II_store)

# Bottleneck stage falls out as argmax of II_*:
contribs = s.cycles_by_loop(L_load, II_load, L_compute, II_compute, L_store, II_store)
# → per-stage contributions to the dataflow expression

# Option B — expand compute, since we've scheduled its inner loops
ii_ck, lat_ck = s_compute.perf_var("compute:k.inner", "ii", "lat")
ii_cj, lat_cj = s_compute.perf_var("compute:j",       "ii", "lat")

expr2 = s.estimate_cycles(L_load, II_load, ii_ck, lat_ck, ii_cj, lat_cj,
                          L_store, II_store)
# Now L_compute and II_compute inside the dataflow expression are
# themselves expressions over the inner loop perf vars. The same
# bottleneck question can be asked at either level.
```

Same compose hierarchy as schedules, applied to the perf model.

### Example 6 — Sharing perf vars and dominance proof

```python
# Two schedules of GEMM that differ only in tile factor
s_a = allo.customize(gemm); s_a.split("k", 8); s_a.pipeline("k.inner")
s_b = allo.customize(gemm); s_b.split("k", 4); s_b.pipeline("k.inner")

ii_a, lat_a = s_a.perf_var("gemm:k.inner", "ii", "lat")
ii_b, lat_b = s_b.perf_var("gemm:k.inner", "ii", "lat")
# ii_a is ii_b   →   True    (uniqued)
# lat_a is lat_b →   True

expr_a = s_a.estimate_cycles(ii_a, lat_a)
expr_b = s_b.estimate_cycles(ii_b, lat_b)
# expr_a = M*N*(K/8)*((8-1)*ii + lat)
# expr_b = M*N*(K/4)*((4-1)*ii + lat)

delta = sympy.simplify(expr_a - expr_b)
# → M*N*K * (5*ii - lat) / 8

# When does s_a strictly dominate s_b?
sympy.solve(delta < 0, lat)
# → lat > 5*ii
# Concretely, for lat=12, ii=1: delta = M*N*K*7/8  → s_a wins.
```

Without uniquing, you'd get `ii_a − ii_b` and `lat_a − lat_b` even though those refer to the same physical thing — `simplify` couldn't cancel them. Sharing is what makes dominance proofs (and pruning of strictly-dominated schedules in an auto-scheduler) possible.

### Example 7 — User-supplied perf info with provenance (AXI loop)

Some loops have IIs the compiler genuinely cannot derive from the IR — a loop reading from off-chip DRAM through an AXI master, a call to a black-box vendor IP, a loop whose stall behavior depends on the memory system. For those, the user concretizes directly and records *why*.

```python
def conv2d(input: "float32[H,W,C]", weight: ..., output: ...):
    for h, w in allo.grid(H, W):
        for c in range(C):
            x = input[h, w, c]      # AXI master read, off-chip
            ...

s = allo.customize(conv2d)
s.pipeline("c")
ii_c, lat_c = s.perf_var("conv2d:c", "ii", "lat")

s.estimate_cycles(ii_c, lat_c)
# Builds fine — the loop is fully symbolic. But if we hadn't declared:
#
# PerfModelError: cannot build cycle expression for 'conv2d':
#   loop 'conv2d:c'  missing: ii, lat
#   note: body contains an off-chip AXI load whose II is not derivable
#         from the IR (depends on burst length and memory system latency)
#   fix:  s.perf_var("conv2d:c", "ii", "lat")          # keep symbolic
#      or s.concretize("conv2d:c", ii=..., lat=..., reason=...)

# Suppose we measured this in cosim or read the vendor's AXI spec:
s.concretize(
    "conv2d:c",
    ii=8, lat=20,
    reason="AXI master read, burst=16, measured cosim 2026-04 on U280",
)

# Now the expression simplifies to a numeric form:
expr = s.estimate_cycles()           # () because no free vars left
# = H*W * ((C-1)*8 + 20)

# Provenance survives in s.explain():
s.explain("conv2d:c")
# loop 'conv2d:c'
#   ii  = 8     source: user concretization
#                reason: "AXI master read, burst=16, measured cosim 2026-04 on U280"
#   lat = 20    source: user concretization
#                reason: (same)
#   trips = C   source: IR (affine bound)
```

Two things this gets right:

  1. **Auditable trust.** Six months later, when someone asks "why is the bottleneck loop predicted at 8 cycles per iter?", `s.explain` answers with the original measurement context — not a hardcoded number whose origin nobody remembers.
  2. **Mixable with derived values.** Within the same kernel, some loops have compiler-derived II (from dep-graph analysis), some have user-concretized II (with `reason`), and some are still symbolic. The expression and the explanation both honestly reflect which is which.

The same pattern works for any opaque value: external IP latencies, FFT core throughput from a datasheet, NoC routing latencies — anywhere the user knows something the compiler can't see.
