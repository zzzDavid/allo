## Bugs Fixed (commit 80fb37e)

### 1. Missing `k_passes` parameter (root cause of 126/128 mismatches)

`run_deploy` did not pass `k_passes` to `get_feather_full_matrix_top`, causing it to default to 1. With k_passes=1, the output_accum block loop iterated 24 times (one per tile) instead of 8 (n_tiles / k_passes = 24/3 = 8). Each block should accumulate 3 K-passes before writing to C.

**Fix**: Extract `k_passes` from `trace_info` and pass it to the kernel builder.

### 2. A/B data types (int8 vs int32)

`_write_deploy_input_data` wrote A and B as int8 arrays, but the kernel function signature uses int32 pointers (FeatherModule converts int8->int32 internally). The host.cpp buffer sizes matched int32 (768 bytes for A[16,12]), so int8 data in a 768-byte buffer would be interpreted as int32 by the kernel.

**Fix**: Convert A and B to int32 before writing binary data files.

### 3. Wide pointer throughput patch (non-power-of-2 stride mismatch)

`_patch_load_bufs_for_throughput` rewrites load_buf functions to use wide `ap_uint` DRAM pointers for row-at-a-time reads. For arrays with non-power-of-2 row widths, this creates `ap_uint<384>` (A: 12 int32), `ap_uint<416>` (instructions: 13 int32), and `ap_uint<48>` (birrd_inst: 6 int8).

Combined with `max_widen_bitwidth=512`, HLS rounds the AXI bus to the next power-of-2:
- `ap_uint<384>` -> 512-bit bus (dataWidth=512 in kernel.xml)
- `ap_uint<416>` -> 512-bit bus
- `ap_uint<48>` -> 64-bit bus

This causes HLS to pad each element to the bus-aligned stride (64 bytes instead of 48 for A), while the host writes data at the natural element stride (48 bytes). Result: every element after the first is misaligned by an increasing offset.

Evidence from kernel.xml port definitions:
```xml
<port name="M_AXI_GMEM0" dataWidth="512"/>  <!-- A: ap_uint<384>, padded to 512 -->
<port name="M_AXI_GMEM1" dataWidth="512"/>  <!-- inst: ap_uint<416>, padded to 512 -->
<port name="M_AXI_GMEM3" dataWidth="512"/>  <!-- B: ap_uint<256>, widened to 512 (OK, power-of-2) -->
```

**Fix**: Disabled the patch. The unpatched kernel uses native int32_t m_axi ports with element-by-element reads. Correct but slower DRAM access.

**Future fix**: Use power-of-2 `ap_uint` types (e.g., `ap_uint<512>` for 12-element rows, extracting 12 values and ignoring 4 padding slots), with matching host-side data padding.

## Architecture

5-kernel dataflow: `dram_loader(1)` -> `pe_array[5,4]` -> `BIRRD[3,2]` -> `output_accum` + `inst_rw`

14 DRAM arguments mapped to 14 HBM pseudo-channels (HBM[0..13]):
- dram_loader: A_pe, inst_pe, loader_m_start, B_pe, inst_w, loader_n_start
- inst_rw: birrd_inst
- output_accum: output_col_map, output_num_m, output_n_base, accum_m_start, accum_n_start, accum_params, C
